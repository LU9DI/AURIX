# Research protocol: parallel text denoising vs autoregressive generation

**Status:** protocol only; no model run or performance claim is included yet.  
**Scope:** isolated research experiment; does not change AURIX runtime or product behavior.

## Research question

Can iterative parallel denoising reduce wall-clock latency for code-generation tasks without reducing the rate of correct, test-passing solutions, under a controlled inference budget?

This is narrower than claiming that diffusion models replace a Claude-Code-scale agent. A positive result would justify a larger study, not establish provider-scale capability.

## Hypotheses

- **H1 (latency):** for a fixed output budget, parallel denoising reduces end-to-end generation latency versus left-to-right generation.
- **H2 (quality):** the denoising model's task pass rate is non-inferior within a pre-registered margin of 5 percentage points.
- **H3 (agent usefulness):** any generation speedup survives compile/test verification and does not disappear when retries and invalid outputs are counted.

A result may support H1 while failing H2/H3. Report these separately.

## Experimental stages

### Stage A — mechanism sanity check

Use a small, controlled corpus of synthetic and held-out code snippets. Compare:
1. autoregressive next-byte/next-patch prediction;
2. iterative masked-span denoising that predicts multiple masked positions per step.

Keep the tokenizer/byte representation, training corpus, train/validation split, parameter count (within 5%), training examples seen, optimizer schedule, and hardware fixed as far as the model families permit. Record unavoidable differences explicitly. This stage tests the mechanism only; it is not a coding-agent benchmark.

**Important:** do not compare the existing float patch model with a separately trained diffusion model and attribute all differences to decoding alone unless training data, parameter count, compute budget, and tuning effort are controlled.

### Stage B — decoding budget sweep

For each model, measure a predeclared grid of inference budgets (e.g. 4, 8, 16, 32, 64 denoising steps, and autoregressive generation until the same maximum output length). Use batch size 1 for interactive latency, then a separate batch-throughput test. Warm up before timing; report median and p90 over at least 5 repetitions per prompt.

Measure:
- wall-clock time to first usable output and total completion time;
- generated bytes/tokens per second;
- peak resident memory and, when supported, energy;
- output length and truncation rate;
- bits per byte/perplexity only as a language-model diagnostic, not as a substitute for task success.

A simulated ternary implementation running on float kernels must not be described as faster or more energy efficient.

### Stage C — coding-task evaluation

Use a fixed, versioned set of tasks that can run in an isolated temporary workspace. Include:
- small bug fixes with unit tests;
- code completion with exact expected behavior;
- multi-file changes only after single-file tasks work reliably.

Each task must specify a clean starting revision, prompt, timeout, allowed tools, test command, and expected result. No network access by default. Keep private/held-out tasks out of training data and prompt examples.

Primary metric: **verified task pass rate** (tests pass and process exits successfully). Secondary metrics: compile/typecheck rate, patch applicability, retries, wall-clock time to verified completion, and resource use. Count timeouts, malformed outputs, and failed attempts in the denominator; do not report only the best sample.

### Stage D — agent loop

Only after Stage C shows a repeatable advantage, evaluate the same model in an agent harness with identical repository snapshots, tool permissions, verification commands, and retry limits. Separate model latency from tool/runtime latency. Memory retrieval and ternary kernels are subsequent ablations, not mixed into the first comparison.

## Reproducibility requirements

- Commit the task manifest and harness version.
- Record repository commit, model/config hash, random seed, runtime/library versions, CPU/GPU details, thread count, and exact command.
- Use at least 3 random seeds for training and 5 timed repetitions per prompt.
- Publish raw per-task JSONL results plus an aggregate summary; do not publish secrets or proprietary task data.
- Report mean and median with bootstrap confidence intervals; retain failures and outliers with reasons.
- Split data by repository/file before training, deduplicate exact and near-duplicate examples, and audit overlap between training and held-out tasks.
- Pre-register the primary metric and non-inferiority margin before running the comparison.

## Decision gates

Proceed to a larger experiment only if:
1. the harness passes a self-test on known-good and known-bad patches;
2. the held-out evaluation is reproducible across seeds;
3. a latency improvement remains after counting verification and retries;
4. the task pass rate is not worse by more than the predeclared 5 percentage points.

If any gate fails, publish the negative/inconclusive result and the failure analysis instead of tuning against the held-out set.

## Limitations

- A small local benchmark cannot establish frontier-level reasoning, repository-scale reliability, or provider economics.
- BPB/perplexity and raw generation speed do not measure useful software engineering by themselves.
- Diffusion can require multiple refinement passes; its wall-clock cost must include every pass.
- Quality comparisons are confounded if architectures, training compute, data exposure, or tuning differ materially.
- This protocol does not claim that the experiment has been executed, that diffusion is faster, or that a useful agent can be built without substantial compute.

## Relationship to the existing ternary patch-LM experiment

The float-vs-ternary results remain separate in [PR #13](https://github.com/LU9DI/AURIX/pull/13). Do not merge those results with diffusion measurements into a single headline. First establish whether parallel denoising improves verified task completion; then test ternary weights and external memory as independent ablations.
